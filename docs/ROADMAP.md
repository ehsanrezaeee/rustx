# RustX roadmap

RustX has delivered four implementation stages. **RP-009 native text editing** is underway on macOS. **RP-008 native interaction** remains open for Windows nested scrolling and a physical Linux desktop replay. Apple Silicon and Linux X11 under Xvfb have passed the nested-scroll focus path.

RustX uses TSX-like markup for authoring and its own runtime and renderer. The performance goals are to match or beat optimized plain JavaScript canvas rendering on the web and to deliver a substantial native speed and responsiveness advantage on equivalent desktop workloads. The [vision implementation guide](VISION_IMPLEMENTATION.md) defines the workloads and how to verify those goals.

## Current stage review

| Stage | Delivered | Stability fixes and remaining work |
| --- | --- | --- |
| 1 · Authoring and lifecycle | Typed markup, mount-once scopes, signals, keyed children, browser and native entry points | Signal callbacks and destructors can access live state without a conflicting runtime borrow. Memos initialize once, and a broad reactive update can settle in one commit. Real browser back/forward cache behavior and full cross-target lifecycle replay remain open. |
| 2 · Shared rendering | Rust layout, shaping, canvas, virtual lists, and CPU/GPU backends | Browser line- and page-mode wheel input is converted to logical pixels. Native wheel events expose both axes to Rust handlers. Native GPU recovery, driver coverage, mixed DPI, and workload-specific frame budgets remain open. |
| 3 · Interaction and services | Forms, text editing, routing, semantics, networking, and platform services | Stacked dialogs restore the correct opener, hidden descendants stay out of the tab order, and native page scrolling brings off-screen keyboard focus into view. The browser updates a projected field when its control type changes. History routing preserves queries at the root URL. Clipboard, file dialogs, pointer capture across the window boundary, physical touch, OS IME, and assistive-technology checks remain open. |
| 4 · Tooling and delivery | Scaffold, CLI, dev reload, editor, web serving, offline shell, and local playground | Windows builds use distinct library and executable names for debug symbols. Web dev reserves its port before building, and web builds protect unrelated output directories. CI builds the current demo from source. Independent onboarding, license/advisory review, and hosted compiler review remain open. |

## Evidence

In a hands-on replay of the Apple Silicon CPU Applications demo, the user selected Japanese – Romaji, typed `kanji` in **About you**, and pressed Space. They reported that the live candidate window appeared near the text caret. A separate native fixture used app-local keyboard events with the live Japanese – Romaji `NSTextInputContext` on macOS 27.0.1. Escape cleared the conversion and restored the original value. Return committed `漢字` once, and Command-Z restored the original value in one undo after keyboard control returned to the app. NSAccessibility supplied value readback. The fixture and logs are in ignored local validation output.

The macOS AppKit fixture reproduced the candidate anchor staying at the end of unchanged Japanese marked text. RustX now uses the UTF-8 selection from Winit while preserving the full marked range for replacement and cancellation. AppKit returned horizontal anchors of 290.0, 328.4, and 309.2 points for a caret at the start, a caret at the end, and the first two characters selected. NSAccessibility reported the corresponding UTF-16 ranges. The updated native demo passed its two-frame CPU smoke, the rebuilt Wasm demo passed Chrome CPU text entry and Tab traversal, and 35 workspace checks passed with the existing loopback check ignored.
