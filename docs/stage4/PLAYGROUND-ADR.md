# ADR-012: compile Rust in an isolated local service, run Wasm in a worker

12 November 2026. RX-46 requires real editable Rust compilation. Precompiled presets do not meet it.

An in-browser rustc would require shipping and maintaining a compiler, sysroot and dependency cache in the browser. A separate compiler service can reuse the pinned Rust 1.90.0 toolchain and audited framework dependencies, with explicit OS isolation and quotas. Choose the latter. Ordinary RustX development does not need Docker. No public deployment or paid service is authorized.

The service binds loopback on a separate origin. It accepts only source text, never Cargo manifests, build scripts or dependencies. A trusted bootstrap invokes the visitor's `app(Scope) -> View`. Direct rustc produces wasm32, never a visitor native executable. Compile workers have an empty environment, read-only toolchain/dependency cache, a private writable directory, no network, bounded CPU/wall time, file size, memory/concurrency and retained output. Source paths are remapped for diagnostics. macOS uses an explicit deny-default sandbox-exec profile; Linux uses bubblewrap when available. Missing or failed isolation disables compilation; there is no unsandboxed fallback. Windows compiler-service availability is a separate verification gate.

Source admission is 32 KiB; two compiles can run concurrently; at most eight retained jobs, five-minute TTL; wall time 30 seconds, CPU 60 seconds per compiler process, output 32 MiB, diagnostics 64 KiB. The initial 15 CPU / 20 wall second budget killed normal framework linking; non-LTO linking also produced duplicate wasm-bindgen enum metadata. The final design uses a smaller CPU-only preview bootstrap, ThinLTO and the explicitly revised bounded budget. These compilation limits are distinct from the unchanged release performance budgets. Jobs have cryptographically random IDs and cancellation kills the process group. Toolchain and framework cache are prepared from locked trusted source before accepting jobs.

Linux applies a 1.5 GiB address-space resource limit. On this actual ARM Mac, setting RLIMIT_AS/RLIMIT_DATA failed with EINVAL; macOS instead samples resident memory for the compiler process tree every 20 ms and stops it above 1.5 GiB. That is a sampled termination threshold, not an instantaneous OS memory ceiling. Failure of memory accounting stops compilation. CPU/file/descriptor limits remain OS-enforced on both implementations. The browser Wasm limit does not bound all browser/JavaScript/driver process memory. Actual OS/provider behavior and remaining deployment/security review are recorded in the acceptance ledger.

The main RustX application remains Rust-authored. Preview output lives in an opaque-origin iframe with scripts only. The visitor module runs in a dedicated worker so loops can be terminated without blocking the editor. Wasm memory is capped at 256 MiB, frame messages are bounded, and a watchdog terminates stalled execution. Rust supplies every visible rectangle, string and pixel. The preview offers only the public fixture GET API, no main-host credentials, storage, clipboard, file, navigation or print capability. CSP limits connections to the dedicated public preview origin. That origin must never host authenticated applications or secrets. Build/runtime errors are reported as errors, never simulated output.

Rollback removes the compile action and declares RX-46 unavailable. It cannot substitute presets and claim acceptance. A hosted deployment would require separate authorization, operational isolation review, HTTPS/CORS/CSP configuration, abuse controls, maintenance/cost ownership and real deployment evidence.

Primary implementation references: [rustc source-path remapping](https://doc.rust-lang.org/nightly/rustc/remap-source-paths.html), [bubblewrap option contract](https://github.com/containers/bubblewrap/blob/main/bwrap.xml). Exact tool versions and measured sandbox outcomes belong in the evidence ledger.
